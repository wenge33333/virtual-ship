# 虚拟商品发货系统 - 需求文档

## 引言

本系统基于开源电商系统 CRMEB_Java（SpringBoot + Mybatis Plus + Redis + Vue + Uniapp）进行最小化二次开发，构建一套独立的虚拟商品自动发货平台。改造策略为最小变更：仅替换品牌标识和移除升级模块，保留原有电商核心功能。系统支持数字权益类、游戏道具/装备、电子卡券/优惠券等多种虚拟商品类型，实现支付后自动发货，并对外提供标准 REST API 供第三方系统集成。系统采用前后端分离部署模式，发货通知仅通过站内消息推送。

二次开发过程中的关键改造包括：去除原开源系统的品牌标识、版权信息及升级/更新检测模块，替换为全新的品牌体系。

## 术语表

- **虚拟商品**：无需物流配送的数字类商品，包括数字权益（会员/订阅/点卡）、游戏道具/装备、电子卡券/优惠券等
- **卡密**：虚拟商品的兑换凭证，格式为卡号+密码或单段兑换码的组合
- **发货**：用户在平台完成支付后，系统将对应卡密信息推送给用户的操作
- **库存单元**：一个独立的卡密记录，包含卡号、密码、面额、有效期等信息
- **自有货源**：商家自备的卡密库存，通过系统后台手动导入管理
- **外部平台**：淘宝/天猫、闲鱼、抖音、拼多多等第三方电商平台

## 需求

### 需求 1：开源系统品牌信息替换

**用户故事：** 作为系统管理员，我希望系统不包含任何原开源系统的品牌标识、版权信息和升级提示，使系统以全新的品牌形象面向用户。

#### 验收标准

1. 系统 SHALL 将前端页面的所有原开源系统品牌名称、Logo、favicon 替换为可配置的全新品牌资源
2. 系统 SHALL 将后端接口返回数据、邮件模板、短信模板中的原开源系统名称替换为可配置的全新名称
3. 系统 SHALL 将代码注释、配置文件中的原开源系统版权声明替换为全新的版权声明
4. 系统 SHALL 将数据库初始化数据中的原品牌相关记录替换为全新品牌数据
5. IF 存在原开源系统的版本更新检测模块，系统 SHALL 完全移除该模块的代码与定时任务
6. IF 存在原开源系统的升级提醒弹窗或通知，系统 SHALL 移除所有升级提醒相关的界面组件与接口

### 需求 2：虚拟商品管理

**用户故事：** 作为运营人员，我希望能够在后台创建和管理各类虚拟商品，设置商品的基本信息、定价和发货规则。

#### 验收标准

1. 系统 SHALL 支持创建数字权益类、游戏道具/装备类、电子卡券/优惠券类及自定义类型的虚拟商品
2. 系统 SHALL 允许运营人员为虚拟商品设置名称、分类、描述、封面图、售价、划线价、库存显示策略
3. 系统 SHALL 允许运营人员为虚拟商品设置发货规则，包括发货内容类型（卡密/固定链接/固定文本）和卡密提取规则（顺序发放/随机发放）
4. 系统 SHALL 支持虚拟商品的上下架状态切换
5. 系统 SHALL 记录每个虚拟商品的创建时间、最后修改时间和操作人

### 需求 3：卡密库存管理

**用户故事：** 作为运营人员，我希望能够批量导入卡密库存，实时查看库存状态，并确保卡密不会被超卖或重复发放。

#### 验收标准

1. 系统 SHALL 支持通过 Excel/CSV 文件批量导入卡密，单次导入上限为 50000 条
2. 系统 SHALL 在导入时校验卡密格式，拒绝含重复卡号或空卡号/密码的记录，返回详细的导入结果（成功数、失败数、失败原因）
3. 系统 SHALL 支持运营人员查看每个虚拟商品的卡密库存总量、已售数量、剩余数量和库存告警阈值
4. 系统 SHALL 在卡密发放时采用数据库行级锁或乐观锁机制，确保同一卡密不会被两个并发订单同时发放
5. 系统 SHALL 支持卡密库存告警，WHEN 库存剩余数量低于设置的告警阈值时，系统 SHALL 向运营人员发送通知
6. 系统 SHALL 支持运营人员手动将已发放但用户退款的卡密标记为可复用，重新加入库存池

### 需求 4：支付后自动发货

**用户故事：** 作为买家，我希望在完成支付后立即获得所购买的虚拟商品卡密，无需等待人工处理。

#### 验收标准

1. WHEN 订单支付状态变更为"已支付"，系统 SHALL 自动触发虚拟商品发货流程
2. 系统 SHALL 在发货完成后将卡密信息展示在用户的订单详情页面中
3. 系统 SHALL 在发货完成后通过站内消息通知用户已发货
4. IF 发货时库存不足，系统 SHALL 将订单标记为"待补货"状态，并向运营人员发送库存不足告警
5. IF 发货过程中发生异常（如数据库写入失败），系统 SHALL 记录异常日志，并在 5 分钟内自动重试最多 3 次
6. 系统 SHALL 在用户订单详情页提供"复制卡密"功能，方便用户快速复制卡号和密码

### 需求 5：多平台订单对接

**用户故事：** 作为技术集成方，我希望系统能够对接淘宝/天猫、闲鱼、抖音、拼多多等外部平台的订单，实现跨平台统一发货管理。

#### 验收标准

1. 系统 SHALL 提供淘宝/天猫平台订单拉取接口，WHEN 授权配置完成后，系统 SHALL 定时拉取授权店铺的虚拟商品订单
2. 系统 SHALL 提供闲鱼平台订单拉取接口，WHEN 授权配置完成后，系统 SHALL 定时拉取授权闲鱼账号的虚拟商品订单
3. 系统 SHALL 提供抖音平台订单拉取接口，WHEN 授权配置完成后，系统 SHALL 定时拉取授权店铺的虚拟商品订单
4. 系统 SHALL 提供拼多多平台订单拉取接口，WHEN 授权配置完成后，系统 SHALL 定时拉取授权店铺的虚拟商品订单
5. 系统 SHALL 支持运营人员在后台为每个平台配置 API 授权信息（AppKey、AppSecret、SessionKey 等）
6. 系统 SHALL 支持设置每个平台的订单拉取间隔时间，最小间隔为 30 秒
7. 系统 SHALL 在外部平台订单拉取成功后，自动创建本地订单记录，并根据商品映射关系触发自动发货
8. IF 外部平台接口调用失败（如鉴权失效、网络超时），系统 SHALL 记录失败日志并在后台展示告警信息

### 需求 6：开放 API 接口

**用户故事：** 作为第三方系统开发者，我希望通过标准 REST API 调用系统的发货能力，将发货功能集成到自己的业务系统中。

#### 验收标准

1. 系统 SHALL 提供基于 API Key + HMAC 签名的认证机制，确保接口调用安全
2. 系统 SHALL 提供 REST API 用于查询虚拟商品列表和详情
3. 系统 SHALL 提供 REST API 用于创建发货订单并触发自动发货
4. 系统 SHALL 提供 REST API 用于查询订单发货状态和卡密信息
5. 系统 SHALL 提供 REST API 用于查询商品卡密库存余量
6. 系统 SHALL 提供 REST API 接口文档页面（Swagger/OpenAPI 格式）
7. 系统 SHALL 记录所有 API 调用的请求日志，包括调用方、接口路径、请求参数、响应状态和耗时
8. 系统 SHALL 对单个 API Key 实施速率限制，默认限制为每分钟 120 次请求

### 需求 7：用户端虚拟商品订单管理

**用户故事：** 作为买家，我希望能够在用户中心查看我的虚拟商品订单，获取已购买的卡密信息。

#### 验收标准

1. 系统 SHALL 在用户订单列表中以显著标识区分虚拟商品订单和实物商品订单
2. 系统 SHALL 在用户订单详情页展示已发放的卡密信息（卡号、密码），并提供一键复制功能
3. 系统 SHALL 在用户端支持虚拟商品订单的退款申请
4. IF 用户申请退款且卡密状态为"未使用"，系统 SHALL 支持自动退款并将卡密回收至库存池
5. IF 用户申请退款但卡密状态为"已使用"，系统 SHALL 将退款申请转入人工审核流程

### 需求 8：后台订单与发货管理

**用户故事：** 作为运营人员，我希望能够在后台管理所有虚拟商品订单，处理异常发货和售后问题。

#### 验收标准

1. 系统 SHALL 在后台订单管理页面展示所有虚拟商品订单，支持按商品类型、订单状态、时间范围、平台来源进行筛选
2. 系统 SHALL 在后台支持运营人员对"待补货"订单进行手动补发货操作
3. 系统 SHALL 在后台展示每条订单的发货日志，包括发货时间、发货卡密、发货结果
4. 系统 SHALL 在后台提供虚拟商品销售统计报表，包括各商品销量、销售额、退款率等指标

### 需求 9：系统安全与稳定性

**用户故事：** 作为系统管理员，我希望系统具备完善的安全防护和稳定运行能力，保障卡密数据不被泄露。

#### 验收标准

1. 系统 SHALL 对数据库中存储的卡密密码字段进行 AES-256 加密存储
2. 系统 SHALL 在用户端展示卡密时进行部分脱敏处理，完整卡密仅在用户主动点击查看或复制时解密展示
3. 系统 SHALL 对卡密库存变更操作记录完整的操作日志，包括操作人、操作时间、操作类型和操作内容
4. 系统 SHALL 在发货链路中实施幂等性控制，确保同一订单不会被重复发货
5. 系统 SHALL 在系统启动时自动检测并记录所有关键依赖服务的可用状态（数据库、Redis、外部平台 API）
